Security Overview ​

SHAVIRA is a security product, so its own security posture matters. This page explains how SHAVIRA turns AI traces into security signal, and how it protects the data you send it — the authentication model, multi-tenant isolation, and data handling as they are actually implemented.

The trace-first security model ​

SHAVIRA treats every LLM call, tool invocation, and agent decision as structured telemetry, then analyzes that telemetry for security issues. Because the data is captured at the trace level, detections have full context: the prompt, the model, the tools used, the end user, and the outcome. Security analysis runs on your observability data rather than as a separate, bolted-on scanner.

Detections → findings pipeline ​

Ingested events → Detection rules (Sigma) → Findings → Triage workflow
  1. Ingest. Events arrive over the SDK endpoint or OTLP and are stored as workspace-scoped rows.
  2. Detect. Sigma-based detection rules — built-in and custom — evaluate against ingested events. Rules carry a severity and optional MITRE ATT&CK technique IDs, and every edit is versioned.
  3. Finding. A match produces a finding with severity, confidence, evidence links, ATT&CK mapping, and detection artifacts (Sigma rule, SIEM query hints).
  4. Triage. Findings move through a workflow — open → investigating → resolved / false_positive — with assignment, comments, and bulk actions. Every action is audit-logged.

Authentication ​

SHAVIRA supports two credential types, each for a distinct caller:

CredentialUsed byHow it's sent
JWT sessionThe web UI (human users)Signed token in an httpOnly cookie
API key (shv_…)SDKs and OTLP exporters (machines)Authorization: Bearer shv_…
  • The web session uses short-lived access tokens with longer-lived refresh, stored in httpOnly cookies so they are not reachable from page JavaScript.
  • API keys are bound to a workspace and, optionally, a single project. A key authenticates which workspace/project the data belongs to — never the content of the data.
  • All API routes except the health check and the auth/ingest receivers sit behind authentication middleware; unauthenticated requests are rejected with 401.

Multi-tenant workspace isolation ​

The workspace is the hard tenant boundary. Isolation is enforced on every read and write, not just at login:

  • Ingest is workspace-bound. Data POSTed with a shv_ key can only ever land in that key's own workspace. A forged or copied ID that points at another tenant simply resolves to "not in this workspace" — no data crosses.
  • Reads are workspace-scoped. Trace, finding, session, end-user, and stream endpoints all filter by the caller's workspace_id. One tenant cannot query another tenant's rows.
  • Per-project RBAC. Within a workspace, access is further scoped by project. Workspace admins see all projects; members and viewers see only projects they belong to. Project roles (admin / analyst / viewer) govern what each member can do. Access checks run on list, detail, session, and live-stream routes alike, and denied cross-project access attempts are logged.

Data handling ​

  • Self-hosted. SHAVIRA runs in your own environment (Docker Compose by default). Trace data lives in your PostgreSQL — it is not sent to a third party.
  • Untrusted content is treated as untrusted. Trace payloads, exception messages, and OTLP span events/links are attacker-influenceable free text. The UI renders them as escaped text (React's default), and the API avoids logging raw payloads, so malicious trace content can't turn into script execution or leak into logs.
  • Input validation at the boundary. Every ingest and API request body is validated against a Zod schema before it is processed or stored.
  • Rate limiting & abuse controls. Login attempts, session/end-user reads, exports, and live SSE connections are each rate-limited per user or per workspace to blunt brute-force and resource-exhaustion attempts.
  • Audit trails. Security-relevant actions — auth events, finding changes, project and membership changes — are written to append-only audit and auth logs.

Secrets in traces

Instrumentation can accidentally capture secrets (tokens, credentials, PII) inside prompts, outputs, or stack traces. SHAVIRA stores and isolates what it receives, but the cleanest defense is to avoid sending sensitive values into traces in the first place. Scrub or redact at the source in your SDK integration.
