Data Model ​

SHAVIRA's data model is built around four core objects: traces, spans, events, and cost records.

Core Objects ​

Trace ​

A trace represents an end-to-end unit of work — typically a single LLM request, agent run, or multi-step workflow. Each trace has:

  • traceId — unique identifier
  • name — descriptive label (e.g., main-chat-flow, incident-summary)
  • eventType — what happened (trace.start, span.end, finding.upsert, cost.record)
  • status — current state
  • metadata — provider, model, environment, service name, instance ID

Span ​

A span is a timed sub-step within a trace. Spans are nested to form a tree:

trace: main-chat-flow
├── span: settings-fetch (120ms)
├── span: model-call (2.3s)
│   └── span: tool-execution (800ms)
└── span: response-format (50ms)

Each span records start/end timestamps, enabling latency analysis at every level.

Event ​

An event is a point-in-time occurrence within a trace. Unlike spans, events have no duration — they record that something happened at a specific moment.

Cost Record ​

Cost records track the financial cost of LLM usage per trace. Costs are resolved in priority order:

TierSourceReliability
VerifiedProvider usage response + model pricing tableHighest
EstimatedToken count from prompt/output text + pricingHigh
ReportedApplication-provided cost valueMedium
UnknownInsufficient informationLowest

Runtime Identity ​

Every trace should carry three identity fields for reliable multi-service observability:

FieldPurposeExamples
service_nameLogical service nameai-chatbot, incident-agent
environmentDeployment contextlocal, staging, prod
instance_idUnique instancehostname+PID, container ID

Use consistent, descriptive names:

Database Schema ​

SHAVIRA uses PostgreSQL with the following key tables:

TablePurpose
usersUser accounts
workspacesWorkspace isolation
engagementsEngagement sessions
tracesTrace records
ingest_eventsRaw ingested events
findingsSecurity findings
finding_commentsFinding discussion threads
detectionsDetection rule definitions
detection_rule_versionsRule version history
model_endpointsRegistered model endpoints
agentsAI agent definitions
cost_ledgerCost attribution records
api_keysAPI key hashes
audit_logAudit trail

Workspace Scoping ​

Every data table includes a workspace_id column. All queries are scoped by workspace, ensuring hard data isolation between tenants.

Session and User Tracking ​

The ingest_events table includes:

  • session_id — groups multi-turn conversations
  • end_user_id — tracks external users

Compound indexes on (workspace_id, session_id) and (workspace_id, end_user_id) enable efficient aggregation.

OTel Columns ​

For OpenTelemetry-ingested spans:

  • otel_trace_id — original OTel trace ID
  • otel_span_id — original OTel span ID

These enable correlation back to the original OTel trace context.
