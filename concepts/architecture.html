Architecture ​

SHAVIRA is a self-hosted platform with a simple three-tier architecture. Your instrumented apps send trace data to the API (over the SDK ingest endpoint or OTLP), the API validates and persists it to PostgreSQL, and the React UI reads it back — with new traces pushed live over SSE.

Components ​

API Server ​

  • Framework: Express 5.1 on Node.js 24
  • Language: TypeScript 5.9 (ESM)
  • Validation: Zod 4.1 for all request/response schemas
  • Database: Raw pg driver (no ORM)
  • Auth: JWT (HS256, 8h access + 30d refresh) + API keys

The API handles:

  • Trace ingestion from SDKs and OTel collectors
  • REST API for the web UI
  • SSE streaming for real-time updates
  • Authentication and authorization
  • Background tasks (archive enforcement, cost recomputation)

Web UI ​

  • Framework: React 19 with Vite 7.1
  • Styling: Custom CSS with dark/light mode
  • State: React hooks (no external state library)
  • Build: Static bundle — no SSR

The web UI is a single-page application served as static files. It communicates with the API server via REST and SSE.

PostgreSQL ​

  • Version: 16
  • Schema: Auto-bootstrapped on API startup
  • Seeding: Demo data created when BOOTSTRAP_DEFAULT_ADMIN=true
  • Migrations: Append-safe — new tables/columns added with IF NOT EXISTS

Event Bus ​

An in-memory publish/subscribe system for real-time trace streaming:

  • Workspace-scoped channels
  • Max 5 concurrent SSE connections per workspace
  • 30-second keepalive heartbeat
  • Best-effort delivery (no persistence)

Data Flow ​

Ingest Flow ​

There are two ways in. The SDK path (POST /api/ingest) accepts SHAVIRA's own event envelope; the OTLP path (POST /v1/traces) accepts standard OpenTelemetry OTLP/JSON and converts spans into the same internal events. Both authenticate with a shv_ API key that binds the data to a workspace (and optional project).

SDK/Collector → POST /api/ingest  (SdkEvent envelope)
             → POST /v1/traces   (OTLP/JSON → convertOtlpToIngestEvents)
    → Zod validation (sdkEventSchema / otlpTracesRequestSchema)
    → ingestEvent() — write to ingest_events (workspace-scoped JSONB payload)
    → Upsert finding      (if type = finding.upsert)
    → Compute cost        (if type = cost.record, or span.end carrying tokens)
    → Publish to event bus (best-effort, for live SSE)
    → 202 { accepted: true }   /   OTLP returns {}

OTLP attribute mapping. When you send OTLP spans, SHAVIRA reads well-known attributes so OTel data lands in the right place:

OTLP attributeMaps to
service.name, deployment.environment (resource)Service / environment identity
shavira.session_id, shavira.user_id (resource or span)Session grouping and end-user attribution
gen_ai.system, gen_ai.request.modelProvider and model
gen_ai.usage.prompt_tokens, gen_ai.usage.completion_tokensToken usage → cost
span events[] / links[]Stored on the event payload and surfaced in trace detail

Query Flow ​

Web UI → GET /api/traces (with filters)
    → Auth middleware (JWT cookie or API key)
    → RBAC check (admin sees all, member sees accessible projects)
    → PostgreSQL query with workspace_id scope
    → Return JSON array

SSE Flow ​

Web UI → GET /api/traces/stream
    → Auth middleware
    → Subscribe to workspace channel on event bus
    → Stream trace.new and finding.new events
    → 30s keepalive heartbeat
    → Cleanup on disconnect

Data Model ​

The schema is bootstrapped automatically on API startup (append-safe CREATE TABLE IF NOT EXISTS). The core tables:

TableHolds
workspacesTop-level tenant boundary — everything is scoped to a workspace
usersWorkspace accounts and roles (admin / member / viewer)
api_keysshv_ ingest keys, bound to a workspace and optional project
projects / project_membersProjects and per-project RBAC grants (admin / analyst / viewer)
ingest_eventsRaw ingested events (JSONB payload) — the source of truth for traces
tracesTrace records with event type, status, and metadata
appsInstrumented services discovered from trace service_name
detection_rules / detection_rule_versionsSigma rules and their version history
detections / findings / finding_commentsDetection artifacts, findings, and triage discussion
model_endpoints / model_prices / model_aliasesModel routing config and synced pricing
cost_ledgerResolved per-event cost for attribution roll-ups
audit_log / auth_logSecurity and access audit trails

Ingested events flow into ingest_events, are projected into traces, priced into cost_ledger, and — when a detection rule matches — produce findings. Every table carries a workspace_id so all reads can be tenant-scoped.
