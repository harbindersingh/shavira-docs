Pricing & Cost Attribution ​

SHAVIRA automatically tracks the cost of every LLM call by syncing model pricing from the LiteLLM pricing catalog and computing per-token costs at ingest time.

How It Works ​

LiteLLM Feed ──→ price_fetch_cache (1h TTL)
                       │
                       ▼
               model_prices table ◄── manual overrides
                       │
                       ▼
           computePricing() at ingest time
                       │
                       ▼
                  cost_ledger
  1. Sync — Every 24 hours the pricing sync service fetches the LiteLLM catalog, diffs it against the current model_prices table, and applies changes automatically.
  2. Compute — When a trace is ingested (via SDK or OTel), SHAVIRA looks up the provider/model in model_prices and computes cost from token counts.
  3. Store — The computed cost, pricing version, and price source are written to the cost_ledger table alongside the raw token counts.

Automatic Sync ​

The pricing sync runs:

  • Once on server startup
  • Every 24 hours thereafter (configurable via PRICING_SYNC_INTERVAL_MS)
  • Up to 3 retries at 5-minute intervals on failure

The sync is non-blocking — a failure never crashes the server. Health status is reported in GET /api/health under the pricingSync field:

json
{
  "ok": true,
  "pricingSync": {
    "lastRunAt": "2026-07-11T02:00:00.000Z",
    "nextRunAt": "2026-07-12T02:00:00.000Z",
    "status": "ok"
  }
}

Change Alerts ​

When any model price changes by more than 20%, SHAVIRA sends alerts through:

  • Slack — if SLACK_WEBHOOK_URL is set
  • Email — if ALERT_EMAIL is set

Alerts include a breakdown of which models changed, old vs. new per-token prices, and the maximum percentage change. New model additions never trigger alerts.

Price Source Tiers ​

Every cost computation is tagged with a priceSource indicating confidence:

SourceMeaning
pricedFull token-level cost computed from catalog pricing
priced_partialCost computed but missing cached token breakdown (cache read/write rates exist but the SDK didn't report cached token counts)
estimatedApproximate cost from partial data
unpriced_missing_modelToken counts present but no pricing entry found for this model
unpriced_missing_usagePricing entry exists but the trace has no token counts
reported_onlyOnly the SDK-reported cost is available (no token counts to verify)

Token Dimensions ​

SHAVIRA computes cost across multiple token dimensions when available:

DimensionDescription
Input tokensPrompt/input tokens
Output tokensCompletion/output tokens
Cached read tokensTokens served from provider cache (e.g., Anthropic prompt caching)
Cached write tokensTokens written to provider cache
Reasoning tokensThinking/reasoning tokens (e.g., Claude extended thinking, OpenAI o-series)

The system detects cached token fields automatically from multiple SDK formats (snake_case, camelCase, nested usage.prompt_tokens_details, etc.).

Model Resolution ​

When looking up prices, SHAVIRA resolves models through a multi-step fallback:

  1. Normalize — Provider and model names are lowercased, version suffixes stripped, namespaces removed (e.g., anthropic.claude-sonnet-4-5-v1 → anthropic / claude-sonnet-4-5)
  2. Alias lookup — Check model_aliases table for canonical names
  3. Exact match — Look for an exact entry in model_prices
  4. Prefix match — Match the longest prefix (e.g., gpt-4o-2024-08-06 matches a gpt-4o prefix entry)
  5. Regex match — Manual regex patterns (admin-created only)

Manual Price Overrides ​

Admins can add custom prices for models not in the LiteLLM catalog (e.g., self-hosted models on Ollama or vLLM):

bash
curl -X POST http://localhost:4000/api/admin/pricing/custom \
  -H "Authorization: Bearer shv_admin_key" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "local",
    "modelPattern": "my-finetuned-llama",
    "matchType": "exact",
    "inputPerToken": 0.00015,
    "outputPerToken": 0.00022,
    "pricingVersion": "custom-2026-07"
  }'

Manual prices (source: "manual") are never overwritten by the automatic sync.

Retroactive Recomputation ​

After a pricing sync or manual override, you can retroactively recalculate costs for historical traces:

bash
curl -X POST http://localhost:4000/api/admin/pricing/recompute \
  -H "Authorization: Bearer shv_admin_key" \
  -H "Content-Type: application/json" \
  -d '{
    "from": "2026-07-01T00:00:00Z",
    "to": "2026-07-11T00:00:00Z",
    "projectId": "proj-001"
  }'

This re-runs computePricing() against the current model_prices for each matching cost_ledger row (batched at 500 rows per call).

Preview & Apply Flow ​

The sync uses a two-step preview/apply flow for safety:

  1. Preview — POST /api/admin/pricing/sync fetches the latest LiteLLM feed, diffs against current prices, and returns a preview with all changes and unknown models. The preview expires after 15 minutes.
  2. Apply — POST /api/admin/pricing/apply applies a preview by ID. If upstream prices changed between preview and apply, a conflict is detected and a fresh preview is returned instead.

The automatic scheduler handles both steps internally. The admin API exposes them for manual control.
