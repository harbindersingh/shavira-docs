Projects ​

Projects organize your traces, findings, and API keys into isolated groups within a workspace. Use projects to separate environments, teams, or applications.

Creating a Project ​

  1. Navigate to the Admin tab
  2. Click New Project
  3. Enter a project name — a URL-friendly slug is generated automatically

Only workspace admins can create projects.

Project Features ​

Trace Isolation ​

Each trace can be tagged to a project. Use project-scoped API keys to automatically tag traces on ingest, or set the projectId field in your SDK.

RBAC ​

Project membership controls who can see project data:

  • Admins see all projects in the workspace
  • Members see only projects they've been added to
  • Workspace-level data (traces without a project) is visible to everyone

Per-Project API Keys ​

Create API keys scoped to a specific project in Settings > API Keys. Traces ingested with a project-scoped key are automatically tagged to that project.

Managing Members ​

  1. In the Admin tab, find the project row
  2. Click the Members icon
  3. Use the checkboxes to add or remove users
  4. Changes save automatically

Members can be assigned roles at the project level.

Project lifecycle: archive, delete & recovery ​

Projects move through a staged lifecycle designed so that no single action permanently destroys data. A project is only ever removed for good after two deliberate admin decisions and two separate recovery windows have elapsed.

All lifecycle actions — archive, delete, restore, and break-glass recovery — are admin-only and audited.

Archiving ​

Archiving a project:

  1. Hides it from the default project list
  2. Starts a 30-day restore window
  3. Shows a warning banner to project members

An archived project keeps all of its data. Nothing is deleted at archive time.

Restore from archive ​

Archived projects can be restored within the 30-day window:

  1. Find the project in the archived list
  2. Click Restore
  3. The 30-day timer is cleared and the project returns to active

If an archived project is never restored, it is eventually tombstoned (see Deleting) and then purged automatically.

Deleting (archived-only, two-step) ​

Hard-delete is only allowed on projects that are already archived — you cannot delete an active project in one step. This two-step gate (archive, then delete) is deliberate: it means a permanent removal always reflects two separate decisions.

Before a delete is confirmed, you are shown the exact blast radius — the full count of records that will be destroyed across the selected projects:

  • Projects
  • Traces
  • Findings
  • Ingest events
  • Cost ledger records
  • API keys
  • Users who will be unlinked from the projects (their workspace access is unaffected)

To proceed you must type a confirmation phrase that encodes the scope — for example delete 12 projects (or delete 1 project for a single project). The phrase is validated against the count the server resolves, so a trivial yes/OK, a stale count, or a mismatched phrase is rejected.

When you confirm, the selected projects are immediately tombstoned — they disappear from every view — and a ~15-day recovery grace window begins. No data is physically deleted yet.

WARNING

Delete is a bulk, instantaneous action across all views. The confirmation phrase is bound to the project count, not the individual project IDs — double-check your selection before confirming.

Break-glass recovery of a deleted project ​

A hard-deleted project is tombstoned, not destroyed. For the ~15-day grace window its data is still physically present and an admin can restore it (break-glass recovery). Recovered projects return to the archived state with a fresh 30-day window.

Recovery is possible for as long as the project has not yet been purged. In production the grace window has a hard floor, so a misconfiguration cannot make a delete instantly permanent.

Permanent purge ​

Once the grace window elapses, an automated job permanently removes the project and all of its data — traces, findings, ingest events, cost ledger records, API keys, project-member links, and the project record itself. After purge there is no recovery path by any means.

A warning email is sent at day 25 of the archive window to workspace admins before a project is tombstoned by the automated timer.

Bulk operations and limits ​

Both archive and delete can be applied to a multi-select of projects in a single action, with per-project checkboxes and select-all in the Admin tab. Per-request caps keep bulk operations safe:

OperationMax per request
Bulk archive500 projects
Bulk delete50 projects

Deletes are capped lower than archives because they are rarer and higher-stakes; delete more than 50 projects as multiple deliberate batches. Requests over the cap are rejected before any work is done. Invalid entries in a batch (not archived, belonging to another workspace, or already deleted) are skipped with a reason rather than failing the whole operation.

Banner Dismissal ​

The archive warning banner can be dismissed per user. Dismissals are archive-cycle-aware — if a project is restored and re-archived, the banner reappears.
